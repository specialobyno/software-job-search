# Software Job Search Workspace

A personal job-search workspace for one software engineer, run with Claude Code. It finds roles, picks or builds the right CV, drafts every application answer, fills the real form in Chrome, submits only after the user's explicit "yes", tracks every application, and prepares for interviews.

**First run:** if `profile.json` → `onboarding.completed` is empty, the user hasn't been onboarded. Suggest `/onboard-me` (and `dependencies.md` if the tools aren't installed) before anything else. `/hunt` and `/apply` refuse to run until onboarding is complete.

## Key files

| File | Purpose |
|------|---------|
| `profile.json` | **Machine-readable facts**: names, contact, right to work, availability, salary, targets, career history (canonical), projects, education, standard answers, writing rules, CV rules. Every skill and script reads it |
| `my_profile.md` | The narrative profile: summary, every role in depth, strengths, what they want next. Written during onboarding |
| `facts.md` | Facts ledger: verified rules, claims made in interviews, crafted answers awaiting confirmation, never-claim list. Read before writing about experience |
| `interview-stories.md` | Reusable STAR interview stories, with **[fill in]** gaps |
| `CV/summary.md` | Index of every CV: positioning, best fit, selection decision tree, content source index |
| `CV/*.pdf` · `CV/source/*.html` | The CVs that can be sent, and their HTML sources (built with `/cv-pdf`) |
| `intake/` | What the user uploaded at onboarding (old CVs, LinkedIn export, documents). Source material only, never sent |
| `found-jobs.md` | Output of `/hunt`: scored roles, chosen CV, `/apply` commands, watchlist |
| `applications.md` | Generated by `/status`. Never edit by hand |
| `jobs/<company>-<role>/` | One folder per application: `forms.md`, `research.md`, `interview-process.md` |
| `.claude/skills/hunt/job-sites.md` | Job sources with the automation allowed for each, plus the ATS company sweep list |
| `.claude/skills/apply/ats-playbooks.md` | How to fill each applicant tracking system (ATS) and which sites have sign-in walls. Add lessons after every application |

## Skills

| Skill | Use |
|---|---|
| `/help-me` | What this repo can do, and what to run next |
| `/onboard-me` | Interactive onboarding: uploads, questions, profile, base CVs. **Run it again any time** to fill gaps or add new information (a new job, project, story, preference) |
| `/hunt [focus\|watchlist]` | Find and score matching jobs, pick a CV for each, save to `found-jobs.md` |
| `/apply <url>[,<url>…]` | Research, choose/tailor the CV, draft every answer, fill the form in Chrome, submit only on an explicit "yes" |
| `/cv-pdf <job folder or CV source>` | Build and verify an ATS-friendly CV PDF from HTML and register it |
| `/status [folder stage note]` | Rebuild `applications.md`, list what needs attention and follow-ups due, update a stage |
| `/interview <folder> [prep]` | Record an interview summary, keep `facts.md` consistent, prepare for the next stage |
| `/inbox [30d]` | Read Gmail for application replies and propose stage updates (read and draft only; needs the Gmail connector) |

## Application folders

`jobs/<company-slug>-<role-slug>/` (e.g. `jobs/stripe-senior-backend-engineer/`) holds `forms.md` (every field with its drafted answer), `research.md` and, once an interview is scheduled, `interview-process.md`.

**Stage line:** every `forms.md` header has `**Stage:** <drafted|filled|blocked|unknown|submitted|interviewing|offer|rejected|withdrawn|closed>` (plus ` · **Applied:** <date>` once sent). `/status` builds `applications.md` from it. A hook lints every `forms.md` write (`.claude/skills/apply/scripts/lint_forms.py`): banned terms, the middle name in a Last Name field, placeholders, a CV that isn't in `CV/`, a missing Stage, the salary rule.

## Hard rules

1. **The user's facts only.** Everything written about the user comes from `profile.json`, `my_profile.md`, `facts.md`, their CVs and their uploads. Never invent employers, titles, dates, qualifications, metrics or technologies.
2. **Career history is canonical.** Titles, employers and dates come from `profile.json` → `career_history`, overriding any old CV. A role's `title_options` are the only alternative titles allowed; its `scope_notes` limit what may be claimed there (e.g. "used AWS, didn't provision it"); its `never_say` terms never appear. A side project's experience is never attributed to an employer.
3. **Crafted answers are flagged.** When a form asks about experience the files don't document, write a realistic answer set in their most fitting real role, label it in `forms.md` ("crafted from <role>: check it matches what you did") and log it in `facts.md` Section 3. Never reuse a Section 3 item as fact; never use Section 4.
4. **Submitting needs an explicit "yes".** Every submission needs the user's "yes, submit" in chat for that specific job. Approval never carries over to another job.
5. **Never:** create accounts or sign in for them, enter passwords, solve CAPTCHAs, enter government ID, tax or bank numbers, apply to a company in `targets.exclude_companies`, send emails or messages without an explicit OK. Sign-in walls → Stage `blocked`; the user submits.
6. **Names** exactly as in `profile.json` (accents included). The middle name goes only in a Middle Name field; full-name fields and CV headers use `full_name`.
7. **Salary rule** (from `profile.json` → `salary`): no range, or `default` inside it → `default`; range top below `default` → the top (flag it if below `minimum`); range bottom above `default` → the middle, rounded to the nearest thousand.
8. **Standing answers** for right to work, availability, pronouns, diversity questions and "how did you hear" come from `profile.json`. Never write anything in `availability.never_say`.
9. **Personal data** stays in this repo. Don't put it in URLs or search queries beyond what an application form needs. Don't store ID numbers, passwords or bank details even if the user pastes them.

## Writing style for form answers

First person, in the user's voice (`profile.json` → `writing.tone`): confident, not boastful, human. Specific examples from their real roles. No bullet points in prose fields. Expand an abbreviation at first use. Avoid over-precise counts that read as AI-written ("six-service", "three exchanges", "60+ features"): say "microservices", "several", "a wide range of" unless the user gave the number and wants it used. Nothing from `writing.avoid`. Cover letters: 3–4 paragraphs. "Why this company" fields use the research gathered by `/apply`.

## Git

This folder is a git repository. Commit at the end of each working session (`git add -A && git commit`), so CVs, skills and forms can always be rolled back. **Push only to a private remote**: `profile.json`, `intake/`, `CV/` and `jobs/` hold personal data. Never push it to the public repo this workspace was cloned from.
